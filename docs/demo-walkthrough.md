### 6. Fetch the approved prompt through Serve

One project-scoped token for Support Desk is stored privately in `secrets/demo-runtime.env`, which Git ignores. It expires seven days after preparation. In a terminal from the repository root:

```bash
set -a
source secrets/demo-runtime.env
set +a
curl --fail --silent --show-error \
  -H "Authorization: Bearer $DEMO_RUNTIME_TOKEN" \
  'http://localhost:8000/serve/v1/prompts/order-reply?env=prod' \
  | .venv/bin/python -m json.tool
```

Alternatively, use the maintained Python CLI directly with the private file (no shell variable setup needed):

```bash
.venv/bin/python scripts/serve-client.py --key order-reply --env prod \
  --token-file secrets/demo-runtime.env
```

The CLI normally reads `PROMPTVAULT_SERVE_TOKEN`; the demo file uses `DEMO_RUNTIME_TOKEN`. The explicit `--token-file` option accepts either name. Sourcing the demo file alone does not set the CLI’s normal environment variable.

Before approval the response is v2; after approving v3 it is v3. Serve returns the approved template, variables and model configuration. **Serve retrieves a prompt; it does not call the LLM or generate an answer.** A downstream application can render/use that snapshot in its own flow.

The token scopes the request to Support Desk, so a matching key in a different project cannot be accessed with it. Only its prefix/hash are stored in PostgreSQL. The private file is a local copy of the one-time displayed secret; do not put it in slides or Git. You can also create a fresh token in API Tokens during the presentation to show one-time disclosure.

### 7. Roll back and revoke

After approving Support Desk v3, open **Admin → Rollback**, choose `order-reply`, target v2 and give a reason such as “Return to the previously reviewed template during the demo.” Call Serve again: it returns v2. Rollback adds an auditable deployment event and updates activation; it preserves the version history.

Finally revoke the showcase runtime token through API Tokens and repeat the curl call; the API should return `401`. This changes the prepared state: for another presentation create a new token and replace the private local value yourself. The preparation helper preserves an existing private token file and does not recover, rotate or silently replace a revoked/expired token.

### 8. Explain accounts, email and collaboration

Authentication uses Argon2id password hashes, signed JWTs and database-backed revocable sessions. The browser keeps a session per tab; the API independently checks active accounts and permissions on each request. Creating/deleting projects and reviewing releases require Super Admin access in the current implementation. Members can work with prompts in projects they are permitted to access.

New registrations must verify a one-use emailed link before login. Existing accounts remain verified. Password reset uses a separate one-use hashed token and revokes prior sessions. Project invitations grant access only after the intended recipient accepts. SMTP authenticates against Gmail and delivers links pointing back to frontend port 5173; it is separate from PostgreSQL and LLM execution.

To demonstrate email, register a spare address you control or request your own password reset. To demonstrate invitations, explicitly invite Jobin, have him sign in and accept his message. No invitations, verification messages or resets were sent during data preparation. Do not complete a password reset mid-presentation unless you intend to change the account password and revoke its sessions.

## How the whole system works

1. **Browser on 5173:** React renders the screens and sends requests to FastAPI on 8000. It does not connect directly to PostgreSQL or hold SMTP/provider credentials.
2. **API on 8000:** validates inputs, resolves the authenticated session, checks project/admin permissions and invokes the application service for that action.
3. **PostgreSQL on 5432:** stores the durable state. `users` and `auth_sessions` handle identity; `projects`, `project_members` and invitations handle collaboration; `prompts` and `prompt_versions` store the library.
4. **Execution:** a version and its input variables determine the rendered prompt. `run_reservations` protects admission and idempotency; the selected adapter runs; `runs` records the outcome. `budgets` and effective `model_pricing` support accounting. Monthly partitions organize the run ledger; analytics views aggregate it.
5. **Release control:** `deployments` records activation, decisions and rollback. `api_tokens` authenticates project-scoped Serve retrieval of the currently active version.
6. **Security and history:** `provider_keys` stores encrypted server-side keys; verification/reset tokens persist only as hashes. `audit_events` captures redacted changes. Database constraints, triggers and transactional functions protect invariants even under concurrent requests.
7. **Startup:** `scripts/start-local.py` checks the persistent local database, applies checksum-validated migrations and starts frontend/backend on fixed ports. It does not reset data or overwrite accounts. Ctrl-C leaves PostgreSQL and saved records intact.

The core data path is: **project → prompt → immutable version → execution evidence → release request → admin decision → active template returned through Serve**.
